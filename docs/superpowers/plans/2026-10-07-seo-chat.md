# Чат-анализ SEO Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Заменить форму SEO-анализа и отдельную SEO-историю на чат: свободный текст, уточняющие вопросы, карточка предложения с чипами подключений, запуск прогона по подтверждению словом и прогресс с отчётом в той же ленте.

**Architecture:** Новый слой чатов — две таблицы в существующем `runs.sqlite3` (миграция `user_version` 4 → 5), строгие правила диалога в домене, сервис с одним вызовом служебной LLM на сообщение и тонкий HTTP-роутер. Прогон не меняется: чат вызывает существующий `SeoService.start`, а прогресс и отчёт читаются существующими эндпоинтами `/api/seo/analyses/**`. Сервер сам решает, что дальше (вопрос, предложение или запуск), и стартует прогон только по подтверждению, сверяя параметры с сохранённым предложением.

**Tech Stack:** Python ≥ 3.13, FastAPI, pydantic v2, SQLite, pytest, ruff; SvelteKit 2 / Svelte 5, TypeScript, Vitest, Tailwind 4; Playwright в `qa`.

**Spec:** `docs/superpowers/specs/2026-10-07-seo-chat-design.md`

## Global Constraints

- Схема БД: `runs.sqlite3`, миграция `user_version` 4 → 5 только добавляет таблицы `seo_chats` и `seo_chat_messages`; существующие таблицы прогонов не меняются, старые прогоны не удаляются.
- Лимиты: сообщение пользователя ≤ 4000 символов; текст ассистента в ленте ≤ 2000 после обрезки; заголовок чата ≤ 80; подключений 1..5; один активный прогон на чат; опрос снимка прогона — 30 секунд.
- Один вызов служебной LLM на отправленное сообщение; разбор не запускает проверок.
- Пользовательские тексты — русские, фиксированные; тело ответа провайдера, адрес и ключ никогда не попадают ни в ответы API, ни в текст ошибок.
- Зависимости только вниз: `app/api` → `app/service` → `app/domain`; `app/db` и `app/integrations` — инфраструктура. Домен не знает про сеть и фреймворки.
- Схемы pydantic — строгие: `ConfigDict(extra="forbid")`, `StrictStr`, как в `app/api/schemas/seo.py`.
- Коды ошибок — как в существующем маппинге `app/api/errors.py`: `ValidationError` и `ConfigurationError` → 400, `ChatNotFound` → 404, `RunConflict` → 409, `StorageError` → 503.
- BFF: бюджет запроса по умолчанию 10 с, для отправки сообщения в чат — 120 с (реальный вызов LLM), как у `/api/seo/settings/test`.
- Коммит после каждой задачи; тест пишется до реализации.

## Review Focus

Входы и условия, которые спека подразумевает, но не описывает подробно; каждому соответствует тест в задаче-владельце.

1. Двойная отправка одного сообщения (двойной клик, повтор запроса): не должно появиться двух прогонов и дублирующихся `seq` — тесты в Task 5 и Task 7.
2. «да» после того, как параметры поменялись после предложения: прогон не стартует, предложение пересобирается — тесты в Task 3 и Task 5.
3. Модель вернула `confirm` без предложения или мусорный JSON: ничего не запускается, черновик цел — тесты в Task 4 и Task 5.
4. Служебная LLM не настроена или отвечает 401: фиксированное сообщение без ключа и тела, прогон не стартует — тесты в Task 6 и Task 7.
5. Долгий вызов LLM: BFF не обрывает запрос на 10 секундах — тест в Task 8.
