Дата: 2026-10-13. Статус: спецификация подготовлена для согласования.

## Цель

Проверять изменения в GitHub Actions и обновлять существующий экземпляр
ИИ-трекера на сервере двумя способами: вручную и автоматически при push тега
с префиксом `v`. Показывать версию реально установленной сборки в интерфейсе.
Обычный push в `main` выполняет CI, но не деплой.

## Запуски и версии

- CI запускается на pull request, push в `main`, push тега `v*` и ручной запуск.
- CD запускается только после успешных проверок для ручного запуска или тега.
- Для тегов разрешены версии `vMAJOR.MINOR.PATCH` и prerelease с суффиксом,
  например `v1.2.3-rc.1`. Неподходящий тег отклоняется до публикации и деплоя.
- Ручной запуск допускает `main` или существующий релизный тег; иные ветки
  отклоняются. Разрешённый ref разрешается в полный SHA один раз.
- Релизный тег должен указывать на коммит из истории `main`.
- Версия сборки из релизного тега совпадает с тегом. Для ручного запуска `main`
  версия имеет вид `sha-<первые 12 символов SHA>`.
- Все последующие шаги используют один SHA: checkout, тесты, сборка, образы,
  manifest деплоя и отображаемая версия. Перемещение `main` во время workflow
  не меняет коммит уже начавшегося запуска.

## CI

Frontend: `npm ci`, проверка типов, Prettier, ESLint, Vitest и production-сборка.
Backend: зависимости по `uv.lock`, pytest с отдельным PostgreSQL 18 service;
тестовые миграции выполняются в случайной схеме, как в текущих фикстурах.
Браузерный изолированный сценарий запускается с Chromium без настоящих ключей
и платных внешних вызовов, включая production frontend под deploy-префиксом.
Docker-сборки обоих сервисов проверяются до деплоя.

Pull request не получает SSH-ключ и права публикации образов. Actions имеют
минимальные права на соответствующую задачу; сторонние actions закрепляются
по полному SHA. Не используются `pull_request_target` и запуск кода PR на сервере.

## Образы и доступ

Backend и frontend собираются в GitHub Actions и публикуются в GHCR. Деплой
использует digest каждого образа; SHA-тег удобен для поиска, но не является
единственным способом идентификации содержимого. Метки OCI содержат commit
и версию. Служба миграций использует тот же backend digest.

Production Compose отделён от локального Compose: он использует готовые
образы, существующее имя проекта и тома, прежние порты и origin.
Публикация пакетов использует `GITHUB_TOKEN`. Серверу для приватных образов
нужен отдельный токен только с доступом на чтение пакетов.

GitHub environment `production` хранит SSH host, port, user, private key,
проверенную запись known_hosts и доступ к GHCR. Для Actions создаётся отдельный
deploy-ключ; личный ключ из локальной SSH-конфигурации не копируется.
Адрес и пользователь задаются конфигурацией, а не интерполируются в shell
из пользовательских workflow inputs.

## Обновление сервера

1. Workflow передаёт deploy-скрипт, production Compose и manifest с SHA,
   версией и digest обоих образов в отдельный каталог релиза.
2. GitHub concurrency и серверный `flock` допускают только один деплой.
   Начавшийся деплой не отменяется новым запуском.
3. До изменения сервисов проверяются manifest, доступность образов, Docker,
   диск и PostgreSQL. Образы скачиваются, пока приложение ещё работает.
4. Проверяются активные замеры. При наличии хотя бы одного запуск завершается
   понятной ошибкой без отмены замеров и без изменения сервисов.
5. Frontend останавливается, закрывая пользовательский запуск новых замеров,
   затем активные замеры проверяются повторно. Если появился замер, frontend
   возвращается и обновление не продолжается; backend и его задачи остаются
   работать. Если замеров нет, останавливается backend. Короткая остановка
   приложения при обновлении допустима; zero-downtime не обещается.
6. Перед миграциями создаются резервная копия PostgreSQL и копия тома настроек.
   Ошибка резервирования блокирует обновление. Копии имеют закрытые права.
7. Отдельным одноразовым контейнером нового backend применяются миграции.
8. Запускаются новый backend и frontend. Проверяются API проектов и HTML
   интерфейса под deploy-префиксом, включая ожидаемую версию сборки.
9. Только после проверок текущий manifest заменяется новым; предыдущий manifest
   и резервная копия остаются доступными для ручного восстановления.

При сбое до миграций можно вернуть предыдущие образы. После начала миграций
не выполняются автоматический downgrade и восстановление БД поверх данных:
workflow сообщает фазу сбоя и путь к резервной копии. Повторный ручной запуск
с прежним релизным тегом допустим только при совместимости схемы; документация
описывает восстановление БД и настроек как отдельную операцию.

Backend не масштабируется, тома не удаляются, `docker compose down -v`,
`docker system prune` и сброс серверного Git checkout не используются.

## Версия в UI

В общей шапке рядом с названием «ИИ-трекинг» показывается небольшая подпись
версии, видимая на всех страницах. Подсказка содержит полный SHA коммита.

Frontend Dockerfile принимает build arguments версии и SHA. Серверная загрузка
общего layout передаёт в страницу только эти публичные метаданные. Версия
зафиксирована при сборке: изменение runtime environment не должно выдавать
другой релиз за содержимое существующего образа. В локальной разработке без
метаданных отображается `dev`.

Проверка версии охватывает релиз, сборку по SHA и локальный fallback. Smoke
проверка после деплоя подтверждает установленную версию по HTML.

## Изменяемые файлы

- `.github/workflows/`: CI и workflow деплоя с ручным и tag-триггером.
- `deploy/`: production Compose, deploy-скрипт и обработка manifest релиза.
- `frontend/Dockerfile`, сборочная конфигурация, общий layout и его загрузка:
  передача и отображение версии.
- Тесты workflow/deploy-инвариантов и версии UI.
- `deploy.md`, корневой README: подготовка environment, секретов, первый запуск,
  ручной деплой, тег, диагностика и восстановление.

## Проверка результата

Проверить YAML workflow, shell-скрипт и production Compose; выполнить frontend
проверки, Vitest, pytest и сборку. Изолированный тест скрипта с подменёнными
Docker/SSH командами проверяет остановку при активном замере, ошибке backup,
ошибке миграции и неуспешном smoke, а также сохранение имен томов и digest.
Затем выполнить реальный ручной workflow и проверить установленную версию.
Тестовый релизный тег не публикуется без выбранного пользователем номера версии.

## Настройка GitHub

Локальный `gh auth status` сообщает недействительную авторизацию. Workflow и
документацию можно подготовить и проверить локально; настройка GitHub secrets
и запуск Actions потребуют действующего доступа. Секреты не сохраняются в Git
и не печатаются в выводе инструментов.
