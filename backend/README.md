# ИИ-трекинг API

Локальный Python API для SEO-анализа сайта и конкурентов и для проверки упоминаний бренда в
ответах ИИ-моделей. Общие инструкции по запуску находятся в [корневом README](../README.md).

## Слои

```
app/
├── main.py          композиционный корень: собирает `app` на уровне модуля
├── core/            сквозные вещи: Settings, иерархия безопасных ошибок
├── domain/          чистые правила: модели, лимиты, валидация, матчинг, SEO-правила и метрики
├── db/              персистентность: providers.json, search-settings.json, seo-settings.json,
│                    runs.sqlite3 и хранилище ключей
├── service/         сценарии: подключения, проверка моделей, поиск, сохранённые прогоны,
│                    SEO-оркестратор и настройки служебной LLM
├── integrations/    исходящие адаптеры: GigaChat, OpenAI-совместимый API, Яндекс, служебная LLM
│                    и SSRF-безопасный обход публичных страниц
└── api/             входящий HTTP: роутеры, зависимости, отображение ошибок
```

`main.py` не содержит фабрики: приложение собирается один раз при импорте, поэтому
`uvicorn app.main:app` не требует вызова. Там же регистрируются middleware, обработчики
ошибок и роутер с префиксом `/api`, а собранные зависимости лежат в `app.state`.

Зависимости направлены внутрь: `api → service → domain`, а `db` и `integrations` реализуют
протоколы, объявленные в `domain`. `domain` и `core` не импортируют FastAPI, httpx или keyring.

Ключи API никогда не покидают `db`: они уходят в системное хранилище (`keyring`, сервис
`ai-tracker`) и не попадают ни в `providers.json`, ни в ответы API, ни в текст ошибок.

## Запуск

```bash
uv sync
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Тот же запуск доступен через `make backend` из корня репозитория.

## Тесты

```bash
uv run pytest
```

Конфигурация pytest живёт в `pyproject.toml` (`pythonpath = ["."]`), поэтому импорт `app`
работает без переменных окружения.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `AI_TRACKER_CONFIG_DIR` | Каталог с `providers.json`, `search-settings.json` и `runs.sqlite3`. По умолчанию `~/.config/ai-tracker` |
| `GIGACHAT_AUTH_KEY` | Запасной ключ для подключения с ID `gigachat` |
| `DEEPSEEK_API_KEY` | Запасной ключ для подключения с ID `deepseek` |
| `GIGACHAT_SCOPE` | Область доступа GigaChat по умолчанию |
| `YANDEX_SEARCH_API_KEY` | API-ключ Yandex Search API; запасное имя — `API_KEY` |
| `YANDEX_SEARCH_FOLDER_ID` | Каталог Yandex Cloud; запасное имя — `FOLDER_ID` |
| `SEO_LLM_ENDPOINT` | Адрес OpenAI-совместимого Chat Completions служебной LLM |
| `SEO_LLM_MODEL` | Модель служебной LLM |
| `SEO_LLM_API_KEY` | API-ключ служебной LLM |

Для Яндекса сохранённые через интерфейс ключ и ID каталога по отдельности имеют приоритет над
соответствующими переменными окружения. Корневой `.env` читается при старте приложения
(`core/config.py:load_env_file`) и **не переопределяет** уже заданные переменные, поэтому явно
экспортированное значение сильнее файла. Если `search-settings.json` отсутствует или не содержит
`enabled`, Яндекс включён.

Настройки Яндекса меняются во вкладке «Поисковые системы» интерфейса. `search-settings.json`
содержит только `enabled` и сохранённый ID каталога; API-ключ хранится в системном хранилище
ключей под отдельной учётной записью `yandex-search`. Пустые строки при обновлении не стирают
учётные данные. Сброс удаляет оба переопределения интерфейса и возвращает независимые значения
окружения; состояние `enabled` сохраняется. Новые настройки действуют для новых задач поиска,
а запущенные задачи сохраняют свой шлюз.

Служебная LLM SEO-анализа настраивается независимо от подключений моделей. Метаданные лежат в
`seo-settings.json` (только адрес и модель), API-ключ — в системном хранилище ключей под
отдельной учётной записью `seo-llm`. Приоритет у значений интерфейса, затем у переменных
`SEO_LLM_ENDPOINT`, `SEO_LLM_MODEL` и `SEO_LLM_API_KEY`; пустой ключ при сохранении не стирает
действующий. Удалённый адрес обязан использовать HTTPS, HTTP и IP-литерал разрешены только для
loopback: это отдельный валидатор `validate_seo_endpoint`, существующий `validate_endpoint`
подключений моделей не ослаблен. Публичный ответ содержит адрес, модель, `has_api_key` и
источники каждого поля, но никогда сам ключ.

## Встроенные подключения

`core/config.py:BUILTIN_PRESETS` пуст: приложение не поставляет предустановленных подключений,
и все подключения создаёт пользователь на экране настроек. Чтобы вернуть шаблоны, достаточно
заполнить этот кортеж — код пресетов (область доступа GigaChat, сброс ключа, только
редактируемый ключ) уже покрыт тестами.

## Группы провайдеров и их модели

Пользовательский провайдер — это группа (`ProviderGroup`): одно имя, один HTTPS-адрес
Chat Completions, один ключ и непустой список моделей (`ProviderModel`). У модели два разных
поля: `id` — стабильный идентификатор внутри приложения, и `model` — идентификатор модели в
API провайдера. Разные модели одной группы делят адрес и ключ, но выбираются по отдельности.

Метаданные лежат в `providers.json` под ключом `groups` в версионированной форме
(`{"version": 2, "groups": [...], "presets": {}}`); ключи остаются в системном хранилище и
адресуются по ID группы. Старая форма с плоским списком `custom` читается как группы из одной
модели: ID прежнего подключения становится одновременно ID группы и ID её модели, поэтому
сохранённый ключ и прежние отметки в форме проверки продолжают работать. Новая форма
записывается только при первом успешном сохранении или удалении — атомарно, через временный
файл, `fsync` и `os.replace`. Битый или неполный старый файл не «починяется» молча: чтение
возвращает понятную ошибку хранилища, а исходный файл и ключ остаются нетронутыми.

Валидация живёт в `domain/provider_groups.py` (имя, адрес, от 1 до 50 моделей, уникальные ID
моделей, отдельные `model` и `name`), сценарий — в `service/provider_settings.py`,
персистентность — в `db/connections.py`. Повторный ID модели — как внутри одной группы, так и
в двух разных — отклоняется до записи.

## HTTP API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/form` | Лимиты, поля нового подключения, области доступа, выбор по умолчанию |
| `GET` | `/api/providers/settings` | Группы провайдеров с их моделями, без ключей |
| `POST` | `/api/providers/settings` | Создать группу провайдера вместе с её моделями |
| `PUT` | `/api/providers/settings/{id}` | Обновить группу: имя, адрес, общий ключ и весь список моделей |
| `DELETE` | `/api/providers/settings/{id}` | Удалить группу, её модели и сохранённый ключ |
| `GET` | `/api/providers` | Плоский список выбора: по одной строке на каждую модель |
| `POST` | `/api/providers` | Совместимость: создать OpenAI-совместимое подключение из одной модели |
| `PUT` | `/api/providers/{id}` | Совместимость: изменить одну модель группы |
| `DELETE` | `/api/providers/{id}` | Совместимость: удалить одну модель; последняя удаляет группу и ключ |
| `POST` | `/api/check` | Прогнать выбранные модели по одним и тем же запросам |
| `GET` | `/api/search/regions` | Справочник регионов Яндекса: `[{id, name}]` |
| `GET` | `/api/search/settings` | Доступность и источники учётных данных Яндекса, без API-ключа |
| `PUT` | `/api/search/settings` | Частично изменить `enabled`, `api_key` и/или `folder_id` |
| `DELETE` | `/api/search/settings/credentials` | Сбросить оба переопределения интерфейса; ответ `200` с публичными настройками |
| `POST` | `/api/search` | Создать задачу поиска сайта в выдаче: `202` и `{id, total, status}` |
| `GET` | `/api/search/{job_id}` | Снимок задачи: `domain`, `regions`, счётчики и пары «вопрос × регион» |
| `POST` | `/api/runs` | Создать сохраняемый прогон моделей, поиска или обоих; ответ `202` с ID |
| `GET` | `/api/runs` | История новыми сверху, по 20 записей с курсором |
| `GET` | `/api/runs/{id}` | Сохранённый снимок со строками и общей таблицей |
| `DELETE` | `/api/runs/{id}` | Удалить завершённый или прерванный прогон; ответ `204` |
| `GET` | `/api/runs/{id}/export.csv` | Выгрузить таблицу завершённого прогона в CSV |
| `GET` | `/api/seo/settings` | Публичные настройки служебной LLM, без ключа |
| `PUT` | `/api/seo/settings` | Частично изменить `endpoint`, `model` и/или `api_key` |
| `DELETE` | `/api/seo/settings/credentials` | Сбросить ключ интерфейса; ответ `200` с публичными настройками |
| `POST` | `/api/seo/settings/test` | Один пробный вызов Chat Completions: `{ok, model, error}` |
| `POST` | `/api/seo/analyses` | Создать SEO-анализ; ответ `202` с `{id, status, estimate}` |
| `GET` | `/api/seo/analyses` | SEO-история новыми сверху, по 20 записей с курсором |
| `GET` | `/api/seo/analyses/{id}` | Снимок: этапы, вход, кандидаты, агрегаты и признаки готовности |
| `GET` | `/api/seo/analyses/{id}/rows` | Постраничная детализация `kind=model` или `kind=search` с ответами моделей |
| `POST` | `/api/seo/analyses/{id}/cancel` | Отменить активный анализ; готовые строки остаются |
| `DELETE` | `/api/seo/analyses/{id}` | Удалить анализ в конечном состоянии; ответ `204` |

Статические маршруты `/api/providers/settings` объявлены раньше динамического
`/api/providers/{id}`, поэтому «settings» не читается как ID подключения; так же
`/api/search/regions` и `/api/search/settings` объявлены раньше `/api/search/{job_id}`.

Публичные настройки имеют вид `{"yandex": {"enabled": true, "folder_id": null,
"has_api_key": false, "api_key_source": "none", "folder_id_source": "none"}}`. Каждый источник
равен `ui`, `env` или `none` независимо от другого. `GET` и ответы на изменение никогда не
содержат API-ключ. `PUT` принимает только необязательные `enabled` (boolean), `api_key` и
`folder_id` (строки); `null` и неизвестные поля отклоняются. `DELETE` успешен даже при отсутствии
сохранённых переопределений.

Группа в ответе содержит `id`, `name`, `kind`, `endpoint`, `configured` и
`models: [{id, model, name}]`. Поля с ключом в ответе нет никогда; пустой или отсутствующий
`api_key` при записи означает «оставить сохранённый ключ».

`GET /api/providers` остаётся плоским списком для главной страницы: одна строка на каждую
модель, где `id` — ID модели, а человекочитаемое имя собирается как `«<провайдер> · <модель>»`.
`POST /api/check` принимает `provider_ids`, и каждый ID означает модель: сервер сам находит её
группу, берёт из неё адрес и ключ и отправляет в API идентификатор `model` этой модели.
Ни адрес, ни ключ из тела запроса не принимаются. От 1 до 5 разных ID: неизвестная или
удалённая модель отклоняется до обращения к внешнему API, а ошибка одной модели не стирает
результаты остальных.

Ошибки возвращаются как `{"detail": "<понятный текст>"}`: 400 — некорректный запрос или
настройки, 503 — недоступное локальное хранилище, 404 — неизвестная задача или прогон,
409 — прогон ещё выполняется и его нельзя удалить или экспортировать.

## Сохранённые прогоны

Форма создаёт один прогон через `/api/runs` и может выбрать модели, регионы Яндекса или обе
ветки. `service/runs.py` записывает задание до внешних запросов, а затем сохраняет каждый
полученный ответ модели и каждую пару «вопрос × регион» через `db/runs.py`. База
`runs.sqlite3` находится в `AI_TRACKER_CONFIG_DIR` и доступна только владельцу процесса.
Ключи API, ID операций Яндекса и сырые заголовки провайдеров туда не записываются.

При старте приложения незавершённые строки старых прогонов помечаются как `interrupted`;
полученные ранее ответы и ссылки сохраняются. Повторной отправки оплачиваемых запросов нет.
История не очищается по времени: пользователь удаляет завершённые и прерванные прогоны сам.
Активный прогон удалить или экспортировать нельзя. CSV содержит только девять колонок общей
таблицы, кодировку UTF-8 с BOM и разделитель `;`; полного текста ответов моделей в нём нет.

## Поиск сайта в Яндексе

Ветка поиска отделена от проверки моделей и живёт по своим правилам:

- `domain/search.py` — чистые правила: нормализация хоста (домен или ссылка http(s), IDN),
  совпадение хоста и поддоменов, каталог регионов, `MAX_SEARCH_PROMPT_LENGTH = 400`,
  `MAX_REGIONS = 5`, `TOP_RESULTS = 10`.
- `integrations/yandex_search.py` — отложенный режим Search API v2: `POST /v2/web/searchAsync`
  (`SEARCH_TYPE_RU`, `FORMAT_XML`, страница 0, плоская группировка по десять документов, регион
  верхним уровнем), затем опрос Operation API и разбор Base64-XML. Любая ошибка превращается в
  фиксированное русское сообщение: тела ответов могут содержать ключ, поэтому они не попадают ни в
  исключения, ни в логи.
- `service/search.py` — задачи в памяти процесса: пары «вопрос × регион» создаются сразу, каждая
  отправляется и опрашивается под общим ограничением параллельности, ошибка одной пары не мешает
  остальным и не считается отсутствием сайта. Идентификаторы задач — `secrets.token_urlsafe`;
  задачи удаляются через 24 часа после создания или через час после завершения, что раньше;
  `close()` отменяет незавершённую работу (вызывается в lifespan вместе с закрытием общего
  `httpx.AsyncClient`).
- Публичный ответ не содержит ни ключа, ни каталога, ни идентификаторов операций Яндекса, ни
  сырого XML: только `id`, `domain`, `regions`, счётчики `total/completed` и строки с
  `status` (`submitting`, `waiting`, `found`, `absent`, `error`), `position`, `url`, `error`.

Прямой `/api/search` остаётся в памяти для совместимости. Сохраняемые прогоны формы идут через
`/api/runs` и используют тот же поисковый сервис с записью полученных строк в SQLite.

## SEO-анализ

Основной сценарий приложения. HTTP-запрос только валидирует вход и создаёт долговечный анализ;
все тяжёлые шаги идут в фоне:

- `domain/seo.py` — вход (URL, сфера, ровно три ключевых запроса, услуги, от одного до пяти
  подключений), фиксированный лимит `GENERATED_QUERY_LIMIT = 20` и минимум пять запросов после
  одного повтора, категории `commercial`/`informational`/`comparative`, объединение услуг
  (введённые первыми), ранжирование кандидатов и признаки бренда. Лимиты прежних `/api/check`,
  `/api/search` и `/api/runs` не меняются.
- `domain/site_fetch.py`, `integrations/site_fetcher.py` — обход публичных HTML-страниц введённого
  хоста и его поддоменов: до 20 страниц, до 1 МиБ на ответ, 10 секунд на соединение и 60 секунд на
  весь обход, до пяти перенаправлений, только публичные IP-адреса с подключением по проверенному
  адресу, соблюдение `robots.txt`, извлечение заголовка и текста стандартной библиотекой.
- `domain/seo_prompts.py` и `integrations/seo_llm.py` — по одному типизированному вызову
  служебной LLM на шаг, ответ разбирается вручную как JSON; агентов, инструментов, `response_format`
  и трассировки нет. Текст страницы передаётся как данные и никогда не попадает в system-сообщение.
- `domain/seo_report.py` — метрики `Metric(denominator, successes, share, average_position)`:
  `share` — доля 0..1 или `None` при пустом знаменателе, `average_position` — `None`, если ничего
  не найдено. В знаменатель входят только строки `found`/`absent`; ошибки, прерывания и отмены
  исключаются и никогда не читаются как отсутствие сайта или упоминания. Метрики кандидата
  считаются по домену, заголовок выдачи остаётся evidence.
- `db/seo.py` — таблицы `seo_analyses`, `seo_stages`, `seo_pages`, `seo_candidates`, `seo_queries`,
  `seo_search_rows`, `seo_candidate_hits`, `seo_model_rows`, `seo_seed_rows` в той же
  `runs.sqlite3`. Репозиторий поднимает `PRAGMA user_version` до 3 (прежние версии 0–2 остаются
  читаемыми для `RunRepository`), включает WAL и `busy_timeout`, пишет каждую строку отдельной
  транзакцией и не создаёт SEO-таблицы в `RunRepository`.
- `service/seo.py` — шесть этапов по порядку (анализ сайта, поиск конкурентов, генерация запросов,
  проверки в ИИ и Поиске, анализ результатов, отчёт). Фатальная ошибка этапов 1 и 3 останавливает
  прогон до платных вызовов; сбой отдельного поиска или модели сохраняется как строка с ошибкой и
  не мешает остальным. Ветви Яндекса и моделей независимы. Отмена конечна. При старте `recover()`
  продолжает опрос уже отправленных отложенных операций Яндекса, а модельные и неотправленные
  строки помечает прерванными. Ошибка хранения останавливает только этот анализ и не трогает
  глобальный механизм остановки `RunService`.
- Отложенный идентификатор операции Яндекса хранится в базе и никогда не возвращается в API;
  ответы моделей отдаёт только постраничный `/rows`, а снимок анализа их не содержит.

Ошибки SEO-маршрутов возвращаются как `{"detail": "..."}`: 400 — некорректный вход, настройки или
отключённый Яндекс, 404 — неизвестный анализ, 409 — попытка удалить активный прогон, 503 —
недоступное хранилище.
