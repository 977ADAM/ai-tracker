# ИИ-трекинг API

Локальный Python API узконаправленного ИИ-трекера: повторяемые замеры видимости бренда
в ответах ИИ-моделей и проверка упоминаний по промптам. Общие инструкции по запуску
находятся в [корневом README](../README.md).

## Мультикомпанийность

API обслуживает несколько компаний в одном инстансе. Компания представлена
проектом с собственным брендом/сайтом, запросами и конкурентами; замеры и история
связаны с ним через `project_id`. Сравнение метрик не пересекает границы проектов.
Настройки подключений моделей и ключи API общие, снимки замеров не содержат ключей.
На каждый проект допускается один активный замер; разные проекты независимы.

## Проекты и замеры

Новые ресурсы: `GET/POST /api/projects`, `GET/PUT/DELETE /api/projects/{id}`,
`GET/POST /api/projects/{id}/measurements`, `GET/DELETE /api/measurements/{id}`,
`GET /api/measurements/{id}/rows?kind=model|search`, `POST /api/measurements/{id}/cancel`.
Создание принимает бренд/сайт и возвращает черновик без запросов и моделей.
Настройка внутри проекта допускает сохранение черновика; запуск требует запросы,
модели, их ключи и служебную LLM. Он возвращает 202 и не ждёт внешних вызовов.
Все пары проверяются последовательным исполнителем. Схему создаёт и меняет
Alembic (`migrations/`); приложение её не мигрирует.

`POST /api/projects/{id}/generate` принимает JSON с kind `description`, `queries`
или `competitors`. Возвращает предложение и не изменяет проект, не запускает замер.
Генерация использует безопасный обход сайта и обычную служебную LLM, общий предел
120 секунд. Проект поддерживает brand_description (≤500) и brand_aliases
(≤20 вариантов по ≤100 символов); старые проекты получают пустые значения.

Импорт промптов: `POST /api/projects/import-prompts`, JSON filename/content (base64).
Поддерживаются TXT/CSV UTF-8 и первый лист XLSX с текстовыми значениями, до 256 КБ;
ответ содержит queries и не сохраняет проект. Query.group — optional, до 100 символов.
Project.include_subdomains определяет область основной доменной метрики. Bare domain
нормализуется в HTTPS; конкурент без URL допустим для текстовых метрик.
Существующие подписи серий обновляются из снимков при старте без внешних вызовов.

## Слои

```
app/
├── main.py          композиционный корень: собирает `app` на уровне модуля
├── core/            сквозные вещи: Settings, иерархия безопасных ошибок и подключение
│                    к PostgreSQL (`database.py`)
├── domain/          чистые правила: модели, лимиты, валидация, матчинг, проекты, метрики ответов
├── db/              персистентность в PostgreSQL: проекты и замеры, прогоны; рядом —
│                    providers.json, search-settings.json, seo-settings.json
│                    и хранилище ключей
├── service/         сценарии: подключения, проверка моделей, поиск, сохранённые прогоны,
│                    замеры проектов, генерация и настройки служебной LLM
├── integrations/    исходящие адаптеры: OpenAI-совместимый API, Яндекс, служебная LLM
│                    и SSRF-безопасный обход публичных страниц
└── api/             входящий HTTP: роутеры, зависимости, отображение ошибок
    └── deps/        композиция: container (сборка сервисов), dependencies (доступ из
                     роутеров)
```

`main.py` не содержит фабрики: приложение собирается один раз при импорте, поэтому
`uvicorn app.main:app` не требует вызова. Там же регистрируются middleware, обработчики
ошибок и роутер с префиксом `/api`, а собранные зависимости лежат в `app.state`.

Зависимости направлены внутрь: `api → service → domain`, а `db` и `integrations` реализуют
протоколы, объявленные в `domain`. `domain` и `core` не импортируют FastAPI, httpx или keyring.

Ключи API никогда не покидают `db`: они уходят в системное хранилище (`keyring`, сервис
`ai-tracker`) и не попадают ни в `providers.json`, ни в ответы API, ни в текст ошибок.

## База данных и миграции

Все постоянные строки живут в PostgreSQL. Слои подключения и доступа:

- `core/database.py` — единственное место, которое знает про драйвер: `connect(dsn)`,
  пул соединений, строки-словари `Row` (доступ и по имени, и по позиции),
  `executemany`/`executescript`, трансляция `?`-плейсхолдеров в `%s`, ошибки драйвера
  (`Error`, `IntegrityError`). Соединение живёт в транзакции от первого оператора до
  `commit()`/`rollback()`; там, где запись сначала читает строку, она берёт её блокировку
  (`SELECT ... FOR UPDATE`).

**Пул соединений.** На каждый адрес базы в процессе создаётся один
`psycopg_pool.ConnectionPool` (минимум одно постоянное соединение, максимум —
`AI_TRACKER_DB_POOL_MAX_SIZE`, по умолчанию 8). `connect()` берёт соединение из пула, а
`close()` возвращает его обратно вместе с откатом незавершённой транзакции, поэтому
повторные операции не платят за новое подключение. Пул закрывается в `lifespan` при
остановке приложения и в конце тестовой сессии; `autocommit=True` (создание и удаление
схемы в тестах) идёт мимо пула и закрывает соединение по-настоящему.

**Логи подключения.** `app.core.database` пишет `INFO` при создании пула
(«Подключение к PostgreSQL установлено: host:port/база, пул 1..8»), `DEBUG` на каждое
физическое соединение и `ERROR` при недоступной базе. Сообщения содержат только
`host:port/базу`: логин, пароль и `options` DSN в лог не попадают. Чтобы увидеть
`DEBUG`, поднимите уровень отдельному логгеру:
`logging.getLogger("app.core.database").setLevel(logging.DEBUG)`.
- `db/schema` больше нет: схему создаёт только Alembic. Каталог миграций —
  `backend/migrations`, конфигурация — `backend/alembic.ini`, адрес базы — та же
  переменная `AI_TRACKER_DATABASE_URL`.

```bash
uv run alembic upgrade head      # создать/обновить схему  (make migrate)
uv run alembic downgrade -1      # откатить последнюю ревизию (make migrate-down)
uv run alembic revision -m "..." # новая пустая ревизия   (make migration name=...)
uv run alembic current           # применённая ревизия
```

Приложение само миграции не выполняет: без `alembic upgrade head` первый же доступ к базе
падает с безопасной ошибкой хранилища. Миграции запускает команда разработчика
(`make migrate` / `uv run alembic upgrade head`) или отдельная служба `migrate` в
`docker-compose.yml` — тот же образ, команда `alembic upgrade head`, и `backend`
стартует только после её успешного завершения. В entrypoint самого backend миграций
нет: при нескольких репликах они бы гонялись за одну схему.

`projects` — корневая таблица: `project_measurements` и `runs` ссылаются на неё через
`project_id NOT NULL ... ON DELETE CASCADE`, поэтому удаление проекта каскадно удаляет
всё, что для него создано.

## Запуск

```bash
createdb ai-tracker             # один раз: база в локальном Postgres.app
uv run alembic upgrade head     # схема
uv sync
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Тот же запуск доступен через `make migrate` и `make backend` из корня репозитория.

Образ для развёртывания собирает `backend/Dockerfile`: зависимости ставятся из `uv.lock`
(`uv sync --frozen --no-dev --extra docker`), приложение запускается от непривилегированного
пользователя, а каталог данных — том `/data`. Дополнительная группа `docker` ставит
файловый бэкенд хранилища ключей: в контейнере нет системного хранилища, и без него экран
настроек не смог бы сохранить ключ. Весь стек поднимается из корня репозитория через
`docker compose up -d --build` (см. корневой README).

## Тесты

```bash
uv run pytest
```

Тестам нужен живой PostgreSQL: набор создаёт случайную схему в
`AI_TRACKER_TEST_DATABASE_URL` (по умолчанию — та же база, что у приложения),
прогоняет в неё миграции через Alembic CLI, очищает таблицы перед каждым тестом и
удаляет схему в конце сессии. Базу приложения тесты не трогают. Внешние HTTP-вызовы
(модели, Яндекс, обход сайтов, служебная LLM) замоканы фикстурами, поэтому платных
запросов тесты не делают.

Конфигурация pytest живёт в `pyproject.toml` (`pythonpath = ["."]`), поэтому импорт `app`
работает без переменных окружения.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `AI_TRACKER_DATABASE_URL` | Адрес PostgreSQL со всеми постоянными строками: проекты, замеры и прогоны. По умолчанию `postgresql://adam977@localhost:5432/ai-tracker` (локальный Postgres.app) |
| `AI_TRACKER_DB_POOL_MAX_SIZE` | Верхняя граница пула соединений на процесс (по умолчанию 8); считайте `воркеры × реплики × значение` против `max_connections` сервера |
| `AI_TRACKER_CONFIG_DIR` | Каталог с `providers.json`, `search-settings.json`, `seo-settings.json` и файлом ключей. По умолчанию `~/.config/ai-tracker` |
| `AI_TRACKER_ALLOWED_HOSTS` | Имена, по которым принимается API, через запятую. По умолчанию `localhost,127.0.0.1`; контейнеру нужно добавить своё имя (`backend`) |
| `DEEPSEEK_API_KEY` | Запасной ключ для подключения с ID `deepseek` |
| `YANDEX_SEARCH_API_KEY` | API-ключ Yandex Search API; запасное имя — `API_KEY` |
| `YANDEX_SEARCH_FOLDER_ID` | Каталог Yandex Cloud; запасное имя — `FOLDER_ID` |
| `SEO_LLM_ENDPOINT` | Адрес OpenAI-совместимого Chat Completions служебной LLM |
| `SEO_LLM_MODEL` | Модель служебной LLM |
| `SEO_LLM_API_KEY` | API-ключ служебной LLM |

Для Яндекса сохранённые через интерфейс ключ и ID каталога по отдельности имеют приоритет над
соответствующими переменными окружения. Корневой `.env` читается при старте приложения
(`core/config.py:load_env_file`) и **не переопределяет** уже заданные переменные, поэтому явно
экспортированное значение сильнее файла. Если `search-settings.json` отсутствует или не содержит
`enabled`, Яндекс включён.

Настройки Яндекса меняются во вкладке «Поисковые системы» интерфейса. `search-settings.json`
содержит только `enabled` и сохранённый ID каталога; API-ключ хранится в системном хранилище
ключей под отдельной учётной записью `yandex-search`. Пустые строки при обновлении не стирают
учётные данные. Сброс удаляет оба переопределения интерфейса и возвращает независимые значения
окружения; состояние `enabled` сохраняется. Новые настройки действуют для новых задач поиска,
а запущенные задачи сохраняют свой шлюз.

Служебная LLM настраивается независимо от подключений моделей. Метаданные лежат в
`seo-settings.json` (только адрес и модель), API-ключ — в системном хранилище ключей под
отдельной учётной записью `seo-llm`. Приоритет у значений интерфейса, затем у переменных
`SEO_LLM_ENDPOINT`, `SEO_LLM_MODEL` и `SEO_LLM_API_KEY`; пустой ключ при сохранении не стирает
действующий. Удалённый адрес обязан использовать HTTPS, HTTP и IP-литерал разрешены только для
loopback: это отдельный валидатор `validate_seo_endpoint`, существующий `validate_endpoint`
подключений моделей не ослаблен. Публичный ответ содержит адрес, модель, `has_api_key` и
источники каждого поля, но никогда сам ключ.

## Встроенные подключения

`core/config.py:BUILTIN_PRESETS` пуст: приложение не поставляет предустановленных подключений,
и все подключения создаёт пользователь на экране настроек. Чтобы вернуть шаблоны, достаточно
заполнить этот кортеж — код пресетов (сброс ключа и единственное редактируемое поле `api_key`)
уже покрыт тестами.

## Группы провайдеров и их модели

Пользовательский провайдер — это группа (`ProviderGroup`): одно имя, один HTTPS-адрес
Chat Completions, один ключ и непустой список моделей (`ProviderModel`). У модели два разных
поля: `id` — стабильный идентификатор внутри приложения, и `model` — идентификатор модели в
API провайдера. Разные модели одной группы делят адрес и ключ, но выбираются по отдельности.

Метаданные лежат в `providers.json` под ключом `groups` в версионированной форме
(`{"version": 2, "groups": [...], "presets": {}}`); ключи остаются в системном хранилище и
адресуются по ID группы. Старая форма с плоским списком `custom` читается как группы из одной
модели: ID прежнего подключения становится одновременно ID группы и ID её модели, поэтому
сохранённый ключ и прежние отметки в форме проверки продолжают работать. Новая форма
записывается только при первом успешном сохранении или удалении — атомарно, через временный
файл, `fsync` и `os.replace`. Битый или неполный старый файл не «починяется» молча: чтение
возвращает понятную ошибку хранилища, а исходный файл и ключ остаются нетронутыми.

Валидация живёт в `domain/provider_groups.py` (имя, адрес, от 1 до 50 моделей, уникальные ID
моделей, отдельные `model` и `name`), сценарий — в `service/provider_settings.py`,
персистентность — в `db/connections.py`. Повторный ID модели — как внутри одной группы, так и
в двух разных — отклоняется до записи.

## HTTP API

Основной сценарий приложения — проекты и их замеры. Всё остальное либо общие
настройки, либо сохранённые ранее маршруты совместимости.

### Проекты и замеры

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/projects` | Карточки проектов (компаний) новыми сверху, по 20 записей с курсором |
| `POST` | `/api/projects` | Создать проект; ответ `201` с сохранённым проектом |
| `POST` | `/api/projects/import-prompts` | Разобрать TXT/CSV/XLSX и вернуть `{queries}`; проект не сохраняется |
| `GET` | `/api/projects/{id}` | Один проект: бренд, сайт, промпты, конкуренты, модели |
| `PUT` | `/api/projects/{id}` | Полностью заменить настройки проекта и поднять `revision` |
| `DELETE` | `/api/projects/{id}` | Удалить проект с его замерами и прогонами; активный замер отвечает `409` |
| `GET` | `/api/projects/{id}/measurements` | История замеров проекта постранично, новыми сверху |
| `POST` | `/api/projects/{id}/measurements` | Запустить замер; ответ `202`, работа идёт в фоне |
| `POST` | `/api/projects/{id}/generate` | Предложение описания, промптов или конкурентов (`kind`), проект не меняется |
| `GET` | `/api/measurements/{id}` | Замер: снимок настроек, прогресс, агрегаты и сравнение с прошлым |
| `GET` | `/api/measurements/{id}/rows` | Постраничная детализация `kind=model` или `kind=search` |
| `POST` | `/api/measurements/{id}/cancel` | Отменить активный замер; готовые строки остаются |
| `DELETE` | `/api/measurements/{id}` | Удалить завершённый замер; активный отвечает `409` |

### Совместимость: проверки, поиск и сохранённые прогоны

Эти маршруты сохранены: они обслуживают `/api/check`, прямой поиск в Яндексе и
сохраняемые прогоны (`runs`). Интерфейс их не использует — основной сценарий идёт
через проекты и замеры, — но контракты и данные остаются рабочими.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/check` | Прогнать выбранные модели по одним и тем же запросам |
| `POST` | `/api/search` | Создать задачу поиска сайта в выдаче: `202` и `{id, total, status}` |
| `GET` | `/api/search/{job_id}` | Снимок задачи: `domain`, `regions`, счётчики и пары «вопрос × регион» |
| `POST` | `/api/runs` | Создать сохраняемый прогон моделей, поиска или обоих; ответ `202` с ID |
| `GET` | `/api/runs` | История новыми сверху, по 20 записей с курсором |
| `GET` | `/api/runs/{id}` | Сохранённый снимок со строками и общей таблицей |
| `DELETE` | `/api/runs/{id}` | Удалить завершённый или прерванный прогон; ответ `204` |
| `GET` | `/api/runs/{id}/export.csv` | Выгрузить таблицу завершённого прогона в CSV |

Статические маршруты `/api/providers/settings` объявлены раньше динамического
`/api/providers/{id}`, поэтому «settings» не читается как ID подключения; так же
`/api/search/regions` и `/api/search/settings` объявлены раньше `/api/search/{job_id}`.

Публичные настройки имеют вид `{"yandex": {"enabled": true, "folder_id": null,
"has_api_key": false, "api_key_source": "none", "folder_id_source": "none"}}`. Каждый источник
равен `ui`, `env` или `none` независимо от другого. `GET` и ответы на изменение никогда не
содержат API-ключ. `PUT` принимает только необязательные `enabled` (boolean), `api_key` и
`folder_id` (строки); `null` и неизвестные поля отклоняются. `DELETE` успешен даже при отсутствии
сохранённых переопределений.

Группа в ответе содержит `id`, `name`, `kind`, `endpoint`, `configured` и
`models: [{id, model, name}]`. Поля с ключом в ответе нет никогда; пустой или отсутствующий
`api_key` при записи означает «оставить сохранённый ключ».

`GET /api/providers` остаётся плоским списком для главной страницы: одна строка на каждую
модель, где `id` — ID модели, а человекочитаемое имя собирается как `«<провайдер> · <модель>»`.
`POST /api/check` принимает `provider_ids`, и каждый ID означает модель: сервер сам находит её
группу, берёт из неё адрес и ключ и отправляет в API идентификатор `model` этой модели.
Ни адрес, ни ключ из тела запроса не принимаются. От 1 до 5 разных ID: неизвестная или
удалённая модель отклоняется до обращения к внешнему API, а ошибка одной модели не стирает
результаты остальных.

Ошибки возвращаются как `{"detail": "<понятный текст>"}`: 400 — некорректный запрос или
настройки, 503 — недоступное локальное хранилище, 404 — неизвестная задача или прогон,
409 — прогон ещё выполняется и его нельзя удалить или экспортировать.

## Сохранённые прогоны

Форма создаёт один прогон через `/api/runs` и может выбрать модели, регионы Яндекса или обе
ветки. `service/runs.py` записывает задание до внешних запросов, а затем сохраняет каждый
полученный ответ модели и каждую пару «вопрос × регион» через `db/runs.py`. Строки лежат в
PostgreSQL (`runs`, `model_rows`, `search_rows`); каждый прогон принадлежит проекту
(`project_id NOT NULL ... ON DELETE CASCADE`). Ключи API, ID операций Яндекса и сырые
заголовки провайдеров туда не записываются.

При старте приложения незавершённые строки старых прогонов помечаются как `interrupted`;
полученные ранее ответы и ссылки сохраняются. Повторной отправки оплачиваемых запросов нет.
История не очищается по времени: пользователь удаляет завершённые и прерванные прогоны сам.
Активный прогон удалить или экспортировать нельзя. CSV содержит только девять колонок общей
таблицы, кодировку UTF-8 с BOM и разделитель `;`; полного текста ответов моделей в нём нет.

## Поиск сайта в Яндексе

Ветка поиска отделена от проверки моделей и живёт по своим правилам:

- `domain/search.py` — чистые правила: нормализация хоста (домен или ссылка http(s), IDN),
  совпадение хоста и поддоменов, каталог регионов, `MAX_SEARCH_PROMPT_LENGTH = 400`,
  `MAX_REGIONS = 5`, `TOP_RESULTS = 10`.
- `integrations/yandex_search.py` — отложенный режим Search API v2: `POST /v2/web/searchAsync`
  (`SEARCH_TYPE_RU`, `FORMAT_XML`, страница 0, плоская группировка по десять документов, регион
  верхним уровнем), затем опрос Operation API и разбор Base64-XML. Любая ошибка превращается в
  фиксированное русское сообщение: тела ответов могут содержать ключ, поэтому они не попадают ни в
  исключения, ни в логи.
- `service/search.py` — задачи в памяти процесса: пары «вопрос × регион» создаются сразу, каждая
  отправляется и опрашивается под общим ограничением параллельности, ошибка одной пары не мешает
  остальным и не считается отсутствием сайта. Идентификаторы задач — `secrets.token_urlsafe`;
  задачи удаляются через 24 часа после создания или через час после завершения, что раньше;
  `close()` отменяет незавершённую работу (вызывается в lifespan вместе с закрытием общего
  `httpx.AsyncClient`).
- Публичный ответ не содержит ни ключа, ни каталога, ни идентификаторов операций Яндекса, ни
  сырого XML: только `id`, `domain`, `regions`, счётчики `total/completed` и строки с
  `status` (`submitting`, `waiting`, `found`, `absent`, `error`), `position`, `url`, `error`.

Прямой `/api/search` остаётся в памяти для совместимости. Сохраняемые прогоны формы идут через
`/api/runs` и используют тот же поисковый сервис с записью полученных строк в PostgreSQL.
Тело `POST /api/runs` требует `project_id`; `GET /api/runs` принимает необязательный
`project_id` и отдаёт историю одного проекта.
