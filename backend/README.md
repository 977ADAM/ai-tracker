# ИИ-трекинг API

Локальный Python API для проверки упоминаний бренда в ответах ИИ-моделей. Общие инструкции по запуску находятся в [корневом README](../README.md).

## Слои

```
app/
├── main.py          композиционный корень: собирает `app` на уровне модуля
├── core/            сквозные вещи: Settings, иерархия безопасных ошибок
├── domain/          чистые правила: модели, лимиты, валидация, матчинг, отчёт
├── db/              персистентность: providers.json и системное хранилище ключей
├── service/         сценарии: подключения, группы провайдеров, проверка, конфигурация формы
├── integrations/    исходящие адаптеры: GigaChat, OpenAI-совместимый API, фабрика
└── api/             входящий HTTP: роутеры, зависимости, отображение ошибок
```

`main.py` не содержит фабрики: приложение собирается один раз при импорте, поэтому
`uvicorn app.main:app` не требует вызова. Там же регистрируются middleware, обработчики
ошибок и роутер с префиксом `/api`, а собранные зависимости лежат в `app.state`.

Зависимости направлены внутрь: `api → service → domain`, а `db` и `integrations` реализуют
протоколы, объявленные в `domain`. `domain` и `core` не импортируют FastAPI, httpx или keyring.

Ключи API никогда не покидают `db`: они уходят в системное хранилище (`keyring`, сервис
`ai-tracker`) и не попадают ни в `providers.json`, ни в ответы API, ни в текст ошибок.

## Запуск

```bash
uv sync
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Тот же запуск доступен через `make backend` из корня репозитория.

## Тесты

```bash
uv run pytest
```

Конфигурация pytest живёт в `pyproject.toml` (`pythonpath = ["."]`), поэтому импорт `app`
работает без переменных окружения.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `AI_TRACKER_CONFIG_DIR` | Каталог с `providers.json`. По умолчанию `~/.config/ai-tracker` |
| `GIGACHAT_AUTH_KEY` | Запасной ключ для подключения с ID `gigachat` |
| `DEEPSEEK_API_KEY` | Запасной ключ для подключения с ID `deepseek` |
| `GIGACHAT_SCOPE` | Область доступа GigaChat по умолчанию |

Сохранённый в настройках ключ всегда имеет приоритет над переменной окружения.

## Встроенные подключения

`core/config.py:BUILTIN_PRESETS` пуст: приложение не поставляет предустановленных подключений,
и все подключения создаёт пользователь на экране настроек. Чтобы вернуть шаблоны, достаточно
заполнить этот кортеж — код пресетов (область доступа GigaChat, сброс ключа, только
редактируемый ключ) уже покрыт тестами.

## Группы провайдеров и их модели

Пользовательский провайдер — это группа (`ProviderGroup`): одно имя, один HTTPS-адрес
Chat Completions, один ключ и непустой список моделей (`ProviderModel`). У модели два разных
поля: `id` — стабильный идентификатор внутри приложения, и `model` — идентификатор модели в
API провайдера. Разные модели одной группы делят адрес и ключ, но выбираются по отдельности.

Метаданные лежат в `providers.json` под ключом `groups` в версионированной форме
(`{"version": 2, "groups": [...], "presets": {}}`); ключи остаются в системном хранилище и
адресуются по ID группы. Старая форма с плоским списком `custom` читается как группы из одной
модели: ID прежнего подключения становится одновременно ID группы и ID её модели, поэтому
сохранённый ключ и прежние отметки в форме проверки продолжают работать. Новая форма
записывается только при первом успешном сохранении или удалении — атомарно, через временный
файл, `fsync` и `os.replace`. Битый или неполный старый файл не «починяется» молча: чтение
возвращает понятную ошибку хранилища, а исходный файл и ключ остаются нетронутыми.

Валидация живёт в `domain/provider_groups.py` (имя, адрес, от 1 до 50 моделей, уникальные ID
моделей, отдельные `model` и `name`), сценарий — в `service/provider_settings.py`,
персистентность — в `db/connections.py`. Повторный ID модели — как внутри одной группы, так и
в двух разных — отклоняется до записи.

## HTTP API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/form` | Лимиты, поля нового подключения, области доступа, выбор по умолчанию |
| `GET` | `/api/providers/settings` | Группы провайдеров с их моделями, без ключей |
| `POST` | `/api/providers/settings` | Создать группу провайдера вместе с её моделями |
| `PUT` | `/api/providers/settings/{id}` | Обновить группу: имя, адрес, общий ключ и весь список моделей |
| `DELETE` | `/api/providers/settings/{id}` | Удалить группу, её модели и сохранённый ключ |
| `GET` | `/api/providers` | Плоский список выбора: по одной строке на каждую модель |
| `POST` | `/api/providers` | Совместимость: создать OpenAI-совместимое подключение из одной модели |
| `PUT` | `/api/providers/{id}` | Совместимость: изменить одну модель группы |
| `DELETE` | `/api/providers/{id}` | Совместимость: удалить одну модель; последняя удаляет группу и ключ |
| `POST` | `/api/check` | Прогнать выбранные модели по одним и тем же запросам |

Статические маршруты `/api/providers/settings` объявлены раньше динамического
`/api/providers/{id}`, поэтому «settings» не читается как ID подключения.

Группа в ответе содержит `id`, `name`, `kind`, `endpoint`, `configured` и
`models: [{id, model, name}]`. Поля с ключом в ответе нет никогда; пустой или отсутствующий
`api_key` при записи означает «оставить сохранённый ключ».

`GET /api/providers` остаётся плоским списком для главной страницы: одна строка на каждую
модель, где `id` — ID модели, а человекочитаемое имя собирается как `«<провайдер> · <модель>»`.
`POST /api/check` принимает `provider_ids`, и каждый ID означает модель: сервер сам находит её
группу, берёт из неё адрес и ключ и отправляет в API идентификатор `model` этой модели.
Ни адрес, ни ключ из тела запроса не принимаются. От 1 до 5 разных ID: неизвестная или
удалённая модель отклоняется до обращения к внешнему API, а ошибка одной модели не стирает
результаты остальных.

Ошибки возвращаются как `{"detail": "<понятный текст>"}`: 400 — некорректный запрос или
настройки, 503 — недоступное локальное хранилище.
